Glaze places every color in [OKHST](https://github.com/tenphi/okhst): OKHSL's
hue and saturation, with the lightness axis replaced by **tone** — a 0–100
axis shaped so that equal tone steps give equal WCAG contrast. This page is the
reference for the color model as Glaze applies it: the transfer math, what tone
does and does not guarantee, and how an authored tone becomes a rendered color
in each scheme. The [OKHST repository](https://github.com/tenphi/okhst) is the
canonical specification of the color space itself: transfer functions,
derivation, and invariants.

To build a palette on this model, continue to
[Designing a palette](./methodology.mdx). Every option and utility named here is
listed in the [API reference](./reference/index.md).

## OKHSL with a tone axis

OKHST keeps OKHSL's hue (`h`, 0–360) and saturation (`s`) verbatim and swaps
the third coordinate:

| Space | Coordinates | Third coordinate                                      |
| ----- | ----------- | ----------------------------------------------------- |
| OKHSL | `h, s, l`   | `l`: perceptual lightness (toe-adjusted OKLab `L`)    |
| OKHST | `h, s, t`   | `t`: tone, a normalized logarithm of luminance        |

You author tone on a 0–100 scale (`tone: 97`). Resolved variants and the
`{ h, s, t }` input object carry it on 0–1, like saturation (hue stays 0–360).

OKHSL lightness is perceptually even, but equal lightness steps produce uneven
contrast: the ratio between neighbors changes along the axis. Tone is shaped so
equal steps produce equal WCAG contrast. Two things follow: a ramp authored in
tone is a contrast-even ladder for free, and dark-mode inversion is a single
subtraction (`100 - t`) instead of a fitted curve.

## The tone transfer

For a gray (`s = 0`) at OKHSL lightness `l`, luminance has a closed form through
the OKHSL toe and the OKLab cube:

```text
Y = toeInv(l)^3     // OKLab L = toeInv(l), cubed
l = toe(cbrt(Y))    // exact inverse
```

Tone is a normalized natural logarithm of `Y`, offset by a small `eps`:

```text
D = ln(1 + eps) - ln(eps)

toneFromY(Y, eps) = 100 * (ln(Y + eps) - ln(eps)) / D
yFromTone(T, eps) = exp(T / 100 * D + ln(eps)) - eps
```

`toTone(l)` and `fromTone(t)` compose these with the gray luminance above, so
they convert between OKHSL lightness (0–1) and tone (0–100) directly. The two
directions are exact analytic inverses: a round trip is lossless to
floating-point precision. `toneFromY(0)` is 0 and `toneFromY(1)` is 100 for any
`eps`, so tone is always a clean 0–100 scale.

### Why `eps` is 0.05

WCAG 2 contrast is `(Y_hi + 0.05) / (Y_lo + 0.05)`. With `eps = 0.05`, tone is a
normalized `ln(Y + 0.05)`, so a fixed tone difference is a fixed ratio of
`Y + 0.05` — a fixed WCAG contrast — wherever it sits on the scale. Since
`ln(1.05) - ln(0.05) = ln(21)`:

```text
ratio(T2, T1) = (Y2 + 0.05) / (Y1 + 0.05)
              = exp((T2 - T1) / 100 * ln(21))
              = 21 ^ ((T2 - T1) / 100)
```

The whole scale is 21:1, black to white, and every 10 tones multiply contrast by
`21 ^ 0.1`, about 1.36. For neutrals:

| Tone | Contrast vs. black |
| ---: | -----------------: |
|   10 |             1.36:1 |
|   20 |             1.84:1 |
|   30 |             2.49:1 |
|   40 |             3.38:1 |
|   50 |             4.58:1 |
|   60 |             6.21:1 |
|   70 |             8.42:1 |
|   80 |            11.42:1 |
|   90 |            15.49:1 |
|  100 |               21:1 |

Inverted, the tone distance between two neutrals for a target ratio `R` is
`100 * ln(R) / ln(21)`:

| Ratio                  | Tone distance |
| ---------------------- | ------------: |
| 3:1 (`'AA-large'`)     |         36.08 |
| 4.5:1 (`'AA'`)         |         49.40 |
| 7:1 (`'AAA'`)          |         63.92 |

These distances are exact for neutrals only. The next section explains why.

## Same tone, same lightness

`okhstToOkhsl({ h, s, t })` passes `h` and `s` through unchanged and sets
`l = fromTone(100 * t)`. `fromTone` depends on the tone (and `eps`) alone, and OKHSL's
`l → L` map has no hue or saturation term: `h` and `s` enter only the chroma
math. That gives OKHST its core invariant:

> A given tone yields the same OKHSL lightness for every hue and saturation.

OKHST inherits OKHSL's gamut and reversibility exactly: every `(h, s, t)` is
realizable and round-trips.

### Uniform in lightness, not luminance

The invariant is about lightness. Equal tone gives equal WCAG and APCA contrast
only for grays: a saturated red and a saturated green at the same tone share an
OKHSL lightness but differ in real luminance `Y`, because hue, saturation, and
gamut mapping all change the final sRGB values. This **chromatic drift** is the
one approximation in the model.

(hue 300, purple) and 4.1 darker (hue 25, red), up to 2.7 tones lighter

saturation and 1.6 at half.

That splits the work between two tools:

- Use **tone deltas** for visual spacing within ramps and between related UI
  colors. The spacing stays even and ordered for every hue.
- Use **`contrast`** when a rendered color must meet a measured WCAG or APCA
  floor. The solver is the one deliberate exception to the invariant: it moves a
  color's tone per hue and saturation until the measured floor is met. See
  [Contrast floors](#contrast-floors-and-verification).

## Tone windows

Each scheme renders authored tone into a **tone window**, configured by
`lightTone` and `darkTone`:

```ts
import { glaze } from '@tenphi/glaze';

glaze.configure({
  lightTone: [10, 100],
  darkTone: [15, 95],
});
```

The window's `lo` and `hi` are **OKHSL-lightness** boundaries (0–100). Glaze
converts them to tone, positions the authored tone linearly in that tone
interval, converts the result back to lightness with the window's `eps`, and
stores it as canonical tone:

```text
loT = toTone(lo / 100, eps)
hiT = toTone(hi / 100, eps)
l   = fromTone(loT + (T / 100) * (hiT - loT), eps)
t   = toTone(l) / 100            // canonical tone (0–1), REF_EPS
```

A window takes three forms:

| Form              | Meaning                                                                         |
| ----------------- | ------------------------------------------------------------------------------- |
| `[lo, hi]`        | Boundaries at the reference `eps`. The common form.                             |
| `{ lo, hi, eps }` | Boundaries plus a render curvature for this scheme. Advanced.                   |
| `false`           | The full range `[0, 100]` at the reference `eps`: no boundaries, same tone curve. |

### Calibrated defaults

|            | `lightTone` | `darkTone` |
| ---------- | ----------: | ---------: |
| `lo`       |          10 |         15 |
| `hi`       |         100 |         95 |
| `eps`      |        0.05 |       0.05 |
| Tone range |    4.95–100 |  9.25–95.9 |

The floors keep mapped tones off pure black in both schemes (OKHSL lightness 10
in light, 15 in dark), and the dark ceiling keeps them short of white at
lightness 95. `eps` is pinned to the reference 0.05 so the axis stays
WCAG-uniform inside the window. Because the remap is linear in tone, it scales
distances between absolute tones uniformly: about 95% of the authored distance
in light and 86.6% in dark.

### High contrast uses the full range

High-contrast variants run the same math with the window forced to the full
range `[0, 100]`, keeping the window's `eps`. There is no separate high-contrast
curve and no fitted dark curve.

### Manual contrast level

A [manual contrast level](./reference/contrast.md#manual-contrast-level) generalizes that bypass
continuously. With `contrastLevel: L` and `f = L / 100`, each boundary moves
toward the full range instead of jumping to it:

```text
lo(f) = lo + (0   - lo) * f
hi(f) = hi + (100 - hi) * f
```

The light default walks `[10, 100] → [0, 100]` and the dark default
`[15, 95] → [0, 100]`; at level 50 they are `[5, 100]` (tone 1.63–100) and
`[7.5, 97.5]` (tone 3.15–97.97). The render `eps` is not interpolated, and a
`false` window is already the full range, so it is level-invariant.

The continuous form applies to the normal variants only. High-contrast variants
are already at the full range, so the level does not widen them further: the
bypass is what keeps the high-contrast tier independent of the level. The level
itself is covered in
[Light, dark, and high contrast](./schemes.mdx#manual-contrast-level).

## Reference and render epsilon

Two `eps` values play separate roles:

- **Reference eps** — `REF_EPS = 0.05`, fixed. It defines the OKHST color
  space and Glaze's canonical tone. `okhst()` input, `{ h, s, t }` input, the
  stored `ResolvedColorVariant.t`, tone deltas, and the contrast solver all use
  it, which keeps tone comparable between schemes.
- **Render eps** — the `eps` of an object tone window. A per-scheme curvature
  control that only changes how authored tone maps through that scheme's
  window. It defaults to the reference value, so by default the two coincide.

When a window's `eps` differs from the reference, Glaze maps with it to land a
final OKHSL lightness, then stores `toTone(l, REF_EPS)`, so deltas and contrast
calculations stay on the reference scale. For example,
`lightTone: { lo: 10, hi: 100, eps: 0.2 }` stores authored tone 50 at 63.89
instead of 52.47: mid tones bend lighter. Most palettes should keep the default.

## The scheme pipeline

A regular color's tone goes through one pipeline per scheme:

```text
authored tone T (0–100)
  -> adaptation mode
       auto + dark    invert: T' = 100 - T
       light / fixed  keep:   T' = T
       static         identity; skip the window
  -> remap into the scheme's tone window (full range for high contrast)
  -> render curvature (window eps) -> OKHSL lightness l
  -> store canonical tone t = toTone(l, REF_EPS) / 100
       // variant { h, s, t, alpha }, t on 0–1
  -> at the rendering edge only:
       fromTone(100 * t) -> l -> sRGB / luminance
optional: a contrast floor searches tone and overrides t
```

### Adaptation modes

The first step is the color's `mode`. Use `auto` for surfaces and foregrounds
that should trade places between light and dark, `fixed` for brand fills and
inverse surfaces that should stay on the same side of the scale, and `static`
for colors that must not adapt.
[Light, dark, and high contrast](./schemes.mdx#adaptation-modes) has the full
table and shows each mode side by side.

**Dark tone inversion is not `autoFlip`.** Inversion is ordinary scheme
adaptation, controlled by `mode`. `autoFlip` solves a different, local problem:
it may mirror a tone delta that overshoots `[0, 100]` to the other side of its
base, or let the contrast solver try the opposite side of a base.

### Hue and saturation pass through

Tone is the only channel OKHST adapts across schemes; `h` and `s` are authoring
inputs that pass through the tone transfer untouched. The one automatic
adjustment is `darkDesaturation`, which dark schemes apply to every color except
`static` ones. A theme, or a single color, can seed a different hue and
saturation for the dark schemes with `darkHue` / `darkSaturation`; those pick the
`h` and `s` that enter the pipeline and never change how tone is transferred.
An authored dark saturation replaces the `darkDesaturation` step instead of
stacking with it: a color's own `darkSaturation` always does, and the theme's
seed does for every color that reads it. A `from` color with no `saturation` of
its own starts from the literal's saturation rather than the seed, so it keeps
the step. `static` colors ignore all of it. The rules are in
[Light, dark, and high contrast](./schemes.mdx#dark-seed) and
[Color definitions](./reference/color-definitions.md#dark-seed-darkhue--darksaturation).

## Tone values

A color's `tone` takes one of three kinds of value. The full syntax, including
`[normal, highContrast]` pairs, is in
[Color definitions](./reference/color-definitions.md#tone-values).

```ts
import { glaze } from '@tenphi/glaze';

const theme = glaze(280, 30);

theme.colors({
  surface: { tone: 97 }, // absolute
  border: { base: 'surface', tone: '-8' }, // tone delta
  deep: { tone: 'min' }, // extreme
  ink: { base: 'surface', tone: 'min' }, // extreme anchored to a base
});
```

### Absolute tone

A number places a color on the 0–100 scale independently of every other color.
Each scheme maps it through the pipeline above, so the stored tone is not the
authored one: `surface: { tone: 97 }` is stored as 97.15 in light and, inverted
to 3 and mapped into the dark window, as 11.85 in dark. A dependent color (one
with a `base`) can still take an absolute tone; it is then mapped on its own and
the base only matters to a `contrast` floor.

### Tone deltas

A signed string is a **tone delta**: the signed difference between a dependent
color and its base.

```ts
border: { base: 'surface', tone: '-8' }
```

How the delta travels depends on the dependent color's `mode`:

- **`fixed` and `static` in every scheme, and `auto` in the light schemes:**
  the delta is applied to the base's resolved tone in that scheme, sign
  preserved. It is an exact tone step, so for neutrals it is an exact contrast
  step.
- **`auto` in the dark schemes:** the delta is applied to the base's *light*
  tone as authored — with the light window's lift taken back out — and the
  result is inverted and mapped through the dark window like an absolute tone.
  In dark high contrast it is the base's light high-contrast tone, which has no
  lift to remove. Order and direction carry over — text that sits below its
  surface in light sits above it in dark — and the step scales with the dark
  window's span: 86.6% of the authored delta at the default windows, on every
  base (a tone-50 base steps `'+4'` to −3.5 and `'-4'` to +3.5). In dark high
  contrast the window is the full range, so the step is exact, only mirrored.

Order carries over only when the base inverts too. An `auto` delta on a
`fixed` or `static` base inverts on its own while the base keeps its side, so
it can cross to the other side of the base in dark: a `'+50'` label on a
`fixed` tone-30 fill sits 50 tones above it in light and about 9 below it in
dark. Make such a dependent `fixed` as well.

If `base + delta` overshoots `[0, 100]`, `autoFlip` (on by default) mirrors the
delta to the other side of the base; if the mirror overshoots too, or `autoFlip`
is off, the delta clamps on its authored side.

### Extremes: `'max'` and `'min'`

`'max'` is author tone 100 and `'min'` is author tone 0. They select the
corresponding end of the scheme without a magic number.

- **Without a base,** an extreme flows through the pipeline like any absolute
  tone: it lands on the window edge and, under `auto`, inverts in dark — `'min'`
  is the darkest color in light and the lightest in dark. Use `fixed` to keep the
  same end without inverting, or `static` to pin one tone everywhere.
- **With a base,** the dark scheme takes a different path. The windows are
  asymmetric, so running the extreme through the dark window would squeeze the
  span between it and its base and cost contrast. Instead Glaze measures the
  tone shift the light scheme produced between the base and the extreme, then
  replays it against the base's resolved dark tone: mirrored under `auto` (both
  ends invert), same-signed under `fixed`. Only `[0, 100]` clamping applies, so
  the color may render past the dark window's edge — on purpose, since you asked
  for the extreme. When the shift does not fit, the color pins at tone 100 or 0.
  `static` colors are unaffected. High-contrast variants follow the same rule,
  but their window is already the full range, so the replay matches the plain
  mapping unless the base itself sits asymmetrically across schemes. With a
  `contrast` floor, an anchored extreme's starting tone is not clamped back
  into the scheme window.

```ts
const neutral = glaze(0, 0);

neutral.colors({
  bg: { tone: 60 },
  fg: { base: 'bg', tone: 'max' },
});
// light: bg 62.0, fg 100.0 (shift +38.0, 3.18:1)
// dark:  bg 43.9, fg 5.9   (shift -38.0, 3.18:1)
```

A root `tone: 'max'` in the same theme lands at the dark window's edge, tone
9.25, and drops to 2.87:1 against `bg` in dark.

## Contrast floors and verification

Tone is the contrast solver's search axis because it is contrast-uniform: the
search converges quickly and WCAG gets a closed-form starting point. But Glaze
never assumes a chromatic color has the luminance of the gray at its tone. It
measures the real color.

`contrast` takes one spec with a pluggable metric: a WCAG ratio (a bare number,
a preset such as `'AA'`, or `{ wcag }`) or an APCA Lc target (`{ apca }`).
Forms, presets, roles, and high-contrast escalation are covered in
[Contrast solving](./contrast.mdx) and
[Contrast and high contrast](./reference/contrast.md).

### How a floor is solved

For a color with `base` and `contrast`, in each scheme Glaze:

1. resolves the base and the color's preferred tone for that scheme, clamped
   into the scheme's tone window (anchored extremes excepted);
2. measures the requested WCAG ratio or APCA Lc at the preferred tone, using the
   color's real hue and saturation — if it already clears the floor with a
   small margin (×1.01 for a WCAG ratio, +0.5 Lc for APCA, to absorb rounding
   in the output formats), the tone is kept (`contrast` is a floor, not a
   target);
3. otherwise searches tone. For WCAG the search starts from the gray tone whose
   luminance hits the ratio exactly — `Y = R * (Y_base + 0.05) - 0.05` on the
   lighter side, `(Y_base + 0.05) / R - 0.05` on the darker — then
   binary-searches against the measured chromatic luminance. For APCA it
   binary-searches against the Lc target directly. The search covers the full
   0–100 range, so a demanding floor can push a color past the window, and it
   aims for the same margin past the target;
4. warns when the target is physically unreachable in the scheme.

```ts
import { glaze } from '@tenphi/glaze';

const theme = glaze(150, 90);

theme.colors({
  surface: { tone: 97, saturation: 0 },
  // 49.4 tones below the surface: exactly 4.5:1 for a neutral
  'step-text': { base: 'surface', tone: '-49.4' },
  // Same starting tone, but the solver measures the real color
  'floor-text': { base: 'surface', tone: '-49.4', contrast: 'AA' },
});
```

### APCA

`apcaContrast(yText, yBg)` implements APCA-W3 0.1.9 (simplified SAPC): a
soft clamp for low luminances and separate exponents for normal and reverse
polarity, returning a signed Lc whose magnitude the solver compares with the
target. Its inputs are APCA **screen luminances** over the gamma-encoded sRGB
channels, not WCAG relative luminance:

```text
Ys = 0.2126 * R^2.4 + 0.7152 * G^2.4 + 0.0722 * B^2.4
```

The soft-clamp constants are calibrated against `Ys`, so the solver feeds APCA
that basis. The implementation omits APCA's font-size lookup that maps an Lc to
a usable text size.

### The drift check

After all four scheme passes, Glaze verifies every color that has a `base` and
a `contrast` floor. It re-measures the color against its base in each scheme, in
the floor's own metric (APCA screen luminance for APCA, WCAG luminance for
WCAG) and with each variant's own `pastel` flag, and emits a `console.warn` when
the result drifts below the target by more than a small slack: 2% of a WCAG
ratio, or 1.5 Lc. Because the solver already measures the real chromatic color,
a floor it meets passes this check. In practice the advisory fires only for an
unreachable floor, next to the solver's "cannot meet" warning for the same
scheme and with the same measured value; it stays as a safety net for the
chromatic approximation. Warnings are deduplicated through a 256-key session
cache that starts over when full. Both warnings are listed in
[Configuration](./reference/configuration.md#warnings).

## Input and output

Glaze parses OKHST wherever it takes a color value — `glaze.color()`, a color
definition's `from`, and the `bg` / `fg` of the standalone `glaze.shadow()` /
`glaze.glow()`:

```ts
import { glaze } from '@tenphi/glaze';

glaze.color('okhst(152 95% 70%)');
glaze.color({ h: 152, s: 0.95, t: 0.7 });
```

Both value forms reproduce the color exactly in the light scheme. The
structured form `glaze.color({ hue: 152, saturation: 95, tone: 70 })` is
different: its `tone` is an authored tone on the 0–100 scale, mapped through the
light window like a theme color, so it renders at tone 71.48. See
[Color tokens](./reference/color-tokens.md#glazecolorinput).

There is no native CSS `okhst()` function, so native exports use `oklch`,
`rgb`, or `hsl`. [Tasty](https://tasty.style) can consume Glaze's custom
serialization, so `tasty()` accepts `format: 'okhst'`, as does `glaze.format()`
for a single variant. `tokens()`, `json()`, `css()`, and `tailwind()` throw and
name a native format instead; the DTCG exports pick a color space of their own.

```ts
const theme = glaze(280, 30);

theme.colors({ surface: { tone: 97 } });
theme.tasty({ format: 'okhst' });
// {
//   '#surface': {
//     '': 'okhst(280 30% 97.15%)',
//     '@media(prefers-color-scheme: dark)': 'okhst(280 27% 11.85%)',
//   },
// }
```

The color formats are listed in
[Output formats](./reference/output.md#color-formats); `toTone`, `fromTone`,
`toneFromY`, `yFromTone`, `okhstToOkhsl`, `okhslToOkhst`, `variantToOkhsl`, and
`REF_EPS` are exported for your own math (see
[Utilities](./reference/utilities.md#okhst-tone-utilities)).

## Bringing existing colors into Glaze

When you move raw CSS colors or design tokens into Glaze, preserve the source
colors first: `glaze.fromHex()` and `glaze.fromRgb()` seed a theme from a
color, `glaze.color()` takes any color value, and a color definition's `from`
places a literal color inside a theme. Then replace one-off values with root
tones, tone deltas, and contrast floors as the relationships become clear.

To carry an OKHSL lightness `L` (0–100) over as a tone, convert it with
`toTone(L / 100)`; the two are not the same number. That tone is still an
authored tone, so the light window remaps it and it renders slightly lighter:
`L` 20 becomes tone 14.36 and renders at lightness 23.8. To keep a source color
exact in light, place it with `from`, which skips the light window, or turn the
window off with `lightTone: false`. The full workflow is in
[Migration and upgrading](./migration.md#migrating-from-an-existing-color-system).
